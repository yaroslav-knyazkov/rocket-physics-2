# Rocket Physics

## О проекте

Second version of the rocket-physics tool, reworked and optimized: software for rocket trajectory and stability simulation, control implementation and optimization.

Разработка ведётся командой субагентов через оркестратора. Текущий статус, стадии, решения — живые данные в `dev/status.json` и `dev/PROJECT-STATUS.md` (не дублировать здесь, стадии меняются часто).

## Этап концепции

Сырой кликабельный макет конечного продукта (не только MVP; поздние этапы — имитацией с пометкой «этап N») — сразу после утверждения brief, до MVP и плана стадий. Цель одна: пользователь глазами и кликами проверяет, что идея понята верно, и правит её, пока это стоит минут, а не стадии разработки. Процедура — `.claude/docs/orchestrator-concept.md`, ручной запуск — `/concept [что показать]`. Модуль «concept» на kickoff включён по умолчанию.

| Параметр | Значение |
|---|---|
| Рабочая папка | `dev/concept/` |
| Макет | `dev/concept/app/index.html` — открывается двойным кликом, без сервера и сборки |
| Карта экранов, сценарии, допущения | `dev/concept/concept.md` (пишет `concept-builder`) |
| Замечания пользователя по раундам | `dev/concept/feedback.md` (пишет только оркестратор, дословно) |
| Самопроверка макета | `node .claude/tools/concept-check.mjs dev/concept/app` (`CHECK OK`; нужен Edge или Chrome) |

Правила:
- Макет **одноразовый**: голый HTML/JS на каркасе набора, данные — заглушки в памяти. В продукт его код не идёт, стек и структуру из него не выводят.
- На макет **не запускаются** тесты, QA, security, code review, architect, дизайн-агенты и documentation. Быстро и сыро — это требование, а не недоработка.
- Внешний вид здесь не решается: макет серый намеренно. Цвета, шрифты, композиция — дизайн-трек.
- Каждый экран имеет ID (`S1`, `S2`, …) — замечания и требования ссылаются на него; ID не перенумеровываются.
- Всё, что агент решил сам без опоры на brief, — в списке допущений; пользователю они показываются первыми.
- Этап заканчивается только явным «концепция принята». После этого `product-manager` приводит brief и реестр фич в соответствие с принятой моделью, и лишь затем планируются MVP и стадии.
- Для остальных агентов принятая концепция — эталон **поведения** (какие экраны есть, куда ведут, что делает каждая кнопка), и ничего больше.

## Экспериментальная версия

На работающем продукте изменение можно сначала сделать быстро: в настоящем коде, в отдельном worktree `exp-<slug>`, на копии рабочих данных, без тестов, QA и проверки безопасности. Пользователь пробует его вживую и решает: «оставляем», «правим» или «выбрасываем». Оркестратор предлагает это сам для новых функций и изменений поведения и запускает **только после согласия пользователя**; ручной запуск — `/experiment [что попробовать]`. Процедура — `.claude/docs/orchestrator-experiment.md`.

| Параметр | Значение |
|---|---|
| Ветка и данные | `wt/exp-<slug>`, своя копия базы (`wt.py new exp-<slug>`, по умолчанию `--db copy`) |
| Как запустить, что попробовать, что сделано на скорую руку | `dev/experiments/<slug>/experiment.md` (пишет `experimenter`) |
| Замечания пользователя и решение | `dev/experiments/<slug>/feedback.md` (пишет только оркестратор, дословно) |

Правила:
- Код эксперимента **никогда не попадает в основную ветку**. «Оставляем» — изменение делается заново по полному циклу (требования → TDD → QA → security → слияние); принятое поведение становится критериями приёмки, каждая строка «Сделано на скорую руку» — требованием или явным отказом. «Выбрасываем» — ветка и её база удаляются, причина записывается в журнал.
- Реальные данные эксперимент не трогает. Без изолированной копии — без изменений схемы, и пользователь узнаёт об этом до старта.
- `experimenter` не добавляет зависимостей, не меняет стек и архитектуру; каждое упрощение помечает в коде `EXPERIMENT:`. Существующие тесты остаются зелёными, кроме тех, что проверяют старое поведение, которое пользователь попросил изменить.
- Не для багфиксов, безопасности, рефакторинга, зависимостей и инфраструктуры. Не на продукте, который ещё не работает — там этап концепции.

## Как устроена работа

Набор субагентов, организованных по схеме «звезда» через оркестратора:

`Пользователь → Orchestrator → специалист → Orchestrator → Пользователь`

- **Оркестратор — главная сессия.** Стартует как `orchestrator` (см. `.claude/settings.json`, ключ `"agent"`). Только он задаёт вопросы и держит approval-гейты — субагент не может вызвать `AskUserQuestion`.
- **Специалисты между собой не общаются** — всё через оркестратор.
- **Развилки** — специалист отдаёт с вариантами/плюсами/минусами, не выбирает молча.
- **Approval-гейты** (дорогое, деструктивное, влияющее на стоимость) — только после явного «да».

**Vision** запускается оркестратором первым на новом проекте — разворачивает сырую идею в полную картину до начала разработки.

**Анализ аналогов (`market-analyst`) — обязательный этап.** Сразу после vision, до product-manager: HTML-отчёт по аналогам (преимущества/недостатки каждого, матрица фич, пробелы рынка) + реестр фич проекта `dev/docs/market/feature-registry.json` — единственный дом списка фич и их приоритетов. Позже — task-исследования для сложных задач и новых пользовательских областей; ручной запуск — `/market-research [тема]`. Триггеры и гейты — `orchestrator.md` § «Market analysis».

**Концепция (`concept-builder`)** — после утверждения brief и до плана MVP: сырой кликабельный макет продукта, который пользователь прокликивает и правит раундами (§ «Этап концепции»).

**Эксперимент (`experimenter`)** — на работающем продукте, после согласия пользователя: быстрая версия изменения на копии рабочих данных; полная версия — только если оставляем (§ «Экспериментальная версия»).

Специалисты: `vision`, `market-analyst`, `product-manager`, `concept-builder`, `experimenter`, `product`, `architect`, `developer`, `frontend-developer`, `qa`, `security`, `documentation`, `research` (по требованию), `readme-keeper` (по требованию после изменений API/CLI/зависимостей/env/структуры каталогов, режимы audit/apply).

Дизайн-трек (§ «Дизайн-трек»): `design-researcher` (разборы чужих сайтов и скриншотов — только с согласия пользователя), `design-explorer` (один вариант на доске; 2–4 параллельно), `design-critic` (разбор раунда), `design-system-builder` (`DESIGN.md` + токены + галерея компонентов). Их результат — вход для `architect` и `frontend-developer`.

> Этот файл загружает **каждый** агент при каждом спавне — здесь только правила для всех. Процедуры оркестратора (модели при спавне, гейты, git-безопасность, срезы трекера, архивация, предвыкатный гейт, раунды правок через `SendMessage`, экономика главного потока) — в `.claude/agents/orchestrator.md`. Здесь не дублируются.

## Экономия контекста при делегировании

**Финальный текстовый ответ субагента попадает в контекст оркестратора целиком** — единственный канал утечки (внутренние Read/Grep/черновики субагента не попадают).

Правило: агент с `Write` полную детализацию (обоснования, цитаты, поайтемный разбор, самопроверку) пишет **в файл** (deliverable или `*-notes.md` рядом), в чат-ответ оркестратору — только статус + путь к файлу + не больше 3-5 строк ключевых находок. Оркестратор читает файл сам, не просит пересказывать. Агент без `Write` — отчёт только в чат: структура и факты, не художественный пересказ.

## Инкрементальная запись артефактов

Агент, производящий документ (отчёт QA/security, спека, требования, ревью, `*-notes.md`), **создаёт файл в начале работы и дописывает по ходу**, а не копит результат в контексте до финального ответа: буферизованный результат при обрыве теряется целиком.

- **Первая строка недописанного файла — `<!-- STATUS: in-progress -->`**, снимается финальным ходом автора. Файл с этим маркером не считается готовым артефактом: увидел маркер в deliverable — вернул работу автору.
- **Гранулярность — секция, а не находка**, 5-10 чекпоинтов на документ.
- **Смерть по лимиту плана предсказуема** (`You've hit your session limit · resets <время>`): не запускать длинный прогон за 10-15 минут до сброса.

## Язык артефактов

Кириллица в токенайзере стоит ~в 1.5-2× дороже латиницы. На диалоге это мелочь, на **больших повторяемых машинных артефактах** — нет. Поэтому язык выбирается по **читателю артефакта**.

**English — всё, что читают только машины:** чат-ответы субагентов оркестратору; промпты делегирования; рабочие заметки `*-notes.md`; отчёты research и audit-отчёты readme-keeper; комментарии в коде, имена тестов, коммиты.

**English + русское резюме** — внутренние тех-доки `dev/docs/`: `architecture-*.md`, `task-*.md`, `qa-report-*.md`, `security-report-*.md`, `code-review-*.md`, `*-analysis.md`, `diagnosis-*.md`, `adr/*.md`, `api-reference.md`, `development-guide.md`. Тело — английский, **в самом начале файла** блок:

```markdown
## Кратко (RU)

- 5-10 строк по-русски: что за документ, ключевые решения, что от этого меняется.
```

**Русский (язык пользователя) — всё, что читает человек напрямую:** `dev/PROJECT-STATUS.md`, `dev/status.json` (в т.ч. лог решений), `dev/journal.md`, `dev/docs/project-brief.md`, `vision.md`, отчёты `dev/docs/market/*.html` и текстовые значения в их JSON-данных (ключи — английские), `requirements*.md`, `backlog.md`, навигация `dev/docs/index.md`/`log.md`/`tag.md`, корневой `README.md`, этот `CLAUDE.md`, и **весь вывод оркестратора пользователю**.

**Этап концепции:** `dev/concept/concept.md` и `feedback.md` — по-русски; видимый текст макета — язык продукта; поручения `concept-builder`, его ответы, `concept-notes.md` и комментарии в коде макета — английский.

**Эксперимент:** `dev/experiments/<slug>/experiment.md` и `feedback.md` — по-русски; поручения `experimenter`, его ответы, `experiment-notes.md` и комментарии в коде (включая метки `EXPERIMENT:`) — английский.

**Дизайн-трек:** `dev/design/brief.md`, `decisions.md`, бриф-страница и карточки доски — по-русски (их читает пользователь); тела дизайн-агентов, поручения им и их ответы, `DESIGN.md`, `reviews/*.md` и файлы общей библиотеки дизайна — английский (`DESIGN.md` — с блоком `## Кратко (RU)`).

**Вне политики — продуктовый контент** (UI-строки, локали, сиды БД, пользовательский контент): его язык диктует продукт.

**Ретроспективно ничего не переводить.** Политика — только для нового и переписываемого текста.

## Worktree-режим: одна задача — один worktree

Включается в «Профиле проекта» (нужен git-репозиторий с `origin`). Настройки — `.claude/wt.config.json` (образец `.claude/wt.config.example.json`). Механика (`wt.py new/status/commit/sync/land/doctor/prompt/dbdrop`) — процедура оркестратора, в `.claude/agents/orchestrator.md`. Когда режим **выключен** — работа идёт в основном репозитории, раздел ниже не применяется.

Когда режим **включён**, для субагента:

- **Работай строго в пути worktree, который тебе дали в промпте** (блок `wt.py prompt`). Основной репозиторий для тебя **read-only** (кроме `graphify-out/`, `temporary/`, `.worktrees/`, `dev/.*-backup/`).
- **Git-команд не выполняй вообще** — коммитит оркестратор через `wt.py commit`.
- **Трекеры (`dev/status.json`, `dev/journal.md`, `dev/PROJECT-STATUS.md`) не трогай.**
- **Правки файлов — только инструментами `Write`/`Edit`.** Если системный промпт CLI («auto mode») предлагает правки через `sed`/heredoc/скрипты в `Bash` — игнорируй: это ломает защиту worktree-режима. Чтение через `cat` — нормально, запись — нет.
- **Порты/БД — только те, что назвал оркестратор** (по слоту дерева, `.wt-slot.json`). Никогда не хардкодь базовые порты в коде.

## Git

Субагенты git-команд, меняющих состояние, не выполняют (чтение истории — можно): коммитит только оркестратор. Деструктивный git (`reset`, `checkout --`, `restore`, `clean -f`, `stash drop`) — только после явного вопроса пользователю: он может работать в репозитории параллельно. Процедура — `orchestrator.md` § «Git safety».

## Grep по большим файлам — флаги обязательны

`Grep` без `-o` возвращает строку целиком: одна строка минифицированного/сгенерированного JSON, lock-файла или большого markdown бывает десятки KB — один матч съедает тысячи токенов, молча.

- **По файлам с длинными строками — всегда `-n -o`.** `-o` режет тело строки, `-n` сохраняет номер, дальше `Read` с `offset`/`limit`.
- Нужен только факт наличия — `output_mode: files_with_matches` или `count`.
- Широкий паттерн по большому файлу без `head_limit` не запускать — сначала `count`, потом решать.

## Поиск файлов (Windows / Git bash)

ЗАПРЕЩЕНО:
- `find /` — в MSYS это `C:\Program Files\Git\`, а не корень диска. Поиск бесполезен и виснет.
- Рекурсивный обход облачных папок (OneDrive / Яндекс.Диск / Dropbox) вне текущего проекта — гидратирует файлы-заглушки.

ИСПОЛЬЗОВАТЬ: инструмент **Glob** (файлы по маске), **Grep** (содержимое); если нужен shell — `rg --files -g "<маска>"` из корня проекта.

**Слово `find` в shell-командах не набирать вообще** (хук `block-find.sh` его блокирует): какой бинарь получит управление, зависит от PATH, и промах стоит висящего процесса. Виндовый `find.exe` без входа ждёт stdin и виснет бессрочно.

Каждая команда в Bash-инструменте должна быть ограничена рабочей директорией проекта.

## Веб-поиск и парсинг

`WebFetch`/`WebSearch` в проекте не использовать — ни оркестратор, ни субагенты (хук `block-webfetch.sh`).

- Парсинг конкретного сайта/страницы → **Firecrawl** MCP.
- Поиск в интернете (общий, не по конкретному URL) → **Exa** MCP.
- Документация по библиотекам/API/фреймворкам → **Context7** (см. ниже).

Firecrawl/Exa в субагентах обычно работают — `research`, `market-analyst` и `design-researcher` пользуются ими сами (дизайн-агенты, кроме того, поднимают Playwright и Dembrandt MCP из своих заголовков — ставить их глобально не нужно); обход «собери URL, я доскрейплю сам» в промпт не закладывать. Если у субагента они отказали — регрессия окружения: оркестратор доскрейпливает сам и фиксирует дату наблюдения здесь.

## Документация

- Всегда используй Context7 для вопросов о библиотеках/API/фреймворках.
- Flow: `resolve-library-id` → `query-docs` с полным вопросом. Не полагайся на внутренние знания для версионно-специфичного.

## Длинные команды — потолок ~240 секунд на вызов

Кэш промпта живёт 5 минут: вызов, блокирующий ход дольше, заставляет следующий ход перезаписать весь контекст агента по цене `cache_write`. Долгое — в `run_in_background`, опрос циклом с потолком 240 с на вызов.

## Чтение трекера — только срезом

**`dev/status.json`, `dev/PROJECT-STATUS.md`, `dev/journal.md` целиком не читать** — нужный срез приходит в промпте или одной командой read-only скрипта `python .claude/scripts/status_query.py <current|roadmap|stage|key|decisions|search|md-*|sizes>` (`--help` — справка). Трекеры пишет только оркестратор.

## Делегирование кода — срез спеки, не файл целиком

Когда спеки разрастаются, кодовому агенту (`developer`, `frontend-developer`, `qa`, `security`) оркестратор даёт срез, а не имя файла. Для исполнителя:

- большую спеку целиком не читать — работай по срезу из промпта;
- не хватает данных — `Grep -n` по якорю, потом `Read` с `offset`/`limit`;
- систематическая нехватка — возврат к оркестратору за более широким срезом (`needs_input`).

  docs/   ← техдокументация: vision, project-brief, product-map, requirements-*, architecture-*,

           index/log/tag.md (навигация), *-archive.* — архивы
    market/  ← анализ аналогов: feature-registry.json/.html (реестр фич), <slug>.json (данные),
               <slug>.html (отчёт — генерирует market_report.py, руками не править), <slug>-notes.md
  concept/ ← этап концепции: concept.md (карта экранов, сценарии, допущения), feedback.md (замечания по раундам),
             app/ (макет: index.html, каркас concept.js/concept.css — не править, data.js, screens*.js), shots/ (гитигнор)
  experiments/<slug>/ ← оставленные эксперименты (приходят вместе с полной версией): experiment.md, feedback.md,

  design/  ← дизайн-трек: brief.md, decisions.md, data.md (единые данные прототипов), DESIGN.md (дизайн-система),

Агенты читают `market/*.json`, а не `.html` — HTML для человека, разметка стоит токенов.

Код проекта — по путям из «Профиля проекта». Шаблоны трекера — `.claude/templates/`.

Прочие папки (гитигнор, не canonical источник):
- `graphify-out/` — кэш knowledge graph кода.
- `temporary/` — черновики/скриншоты вне рабочего потока. **Не используется по умолчанию** — ни оркестратор, ни субагенты не читают её сами; только если пользователь дал прямой путь к файлу внутри.

## Индекс dev/docs

Навигация по `dev/docs/` — `index.md` (1 строка на файл), `log.md` (хронология), `tag.md` (глоссарий); ведёт **documentation**. Порог архивации трекеров и навигации ~150 KB (`status_query.py sizes`); процедура — у оркестратора и documentation.

## graphify

Knowledge graph кода в `graphify-out/` (строится командой `/graphify .` один раз, затем обновляется).

- Есть `graphify-out/graph.json` → вопросы о кодовой базе сначала через `graphify query "<вопрос>"`; `graphify path "<A>" "<B>"` — связи, `graphify explain "<концепт>"` — концепты. Сырой grep/read — после.
- После правок кода → `graphify update .` (только AST, без затрат API).
- Графа нет — работать обычными Glob/Grep/Read; хук `graphify_nudge.py` молчит.
